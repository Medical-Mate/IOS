## 2. 일부러 옮기지 않은 것

**2026-11-20 결정: Figma 기준으로 간다.** 아래 것들은 Figma가 미사용 · 미게시로 표시해
두었으므로 옮기지 않는다. Android가 쓰는 것과 어긋나지만 **Figma가 정본이다.** 화면을
그리다 이 중 하나가 꼭 필요해지면 그때 디자인 트랙에 묻고, 답이 오기 전에는 임의로
만들지 않는다.


### 2.1 `Archive · 참고 (앱 미사용)` 15종 — **Figma가 미사용으로 못박았다**

섹션(`1864:1446`)의 첫 줄이 **"미사용 컴포넌트 15종 · 삭제하지 않고 보관"**이다.
CLAUDE.md 1장의 규칙대로 보지 않았다.

> Bottom CTA Bar · Bottom Sheet · Radio · .Toast · Voice Input · Source Quote ·
> Doctor Card · Segmented Control · Loading · Hospital Card · Picker Field ·
> Todo Row · Card Pick · Add Row · Select Bar

**⚠️ 디자인 트랙 확인 필요.** Android는 이 가운데 여럿을 화면에 쓰고 있다
(`BottomCtaBar` · `BottomSheet` · `Toast` · `Loading` · `SegmentedControl` ·
`HospitalCard` · `PickerField` · `TodoRow` · `CardPick` · `AddRow` · `SelectBar`).
Android `CLAUDE.md`는 "컴포넌트 3.0 신규 7종 모두 화면에 붙었다"고 적었고
Hospital Card는 1e-1, Picker Field·Card Pick·Add Row는 1r-4, Todo Row는 1r-2·1r-4에
쓴다고 했다. **Figma가 미사용으로 옮긴 것인지, 보관함에 중복으로 들어간 것인지
확인해야 한다.** 답이 나오기 전에는 옮기지 않는다.

### 2.2 `홈 · 신규 컴포넌트 (제안 · 미게시)` — **넷 다 옮겼다**

`3313:4910` 프레임 이름이 **제안 · 미게시**다. 그 가운데 **`Link / On Image` ·
`Card / Action` · `Card / Schedule` 셋은 게시된 와이어프레임(`1n-2` · `1n-1`)이
실제로 쓰고 있어** 화면에서 읽어 옮겼다. 프레임이 미게시여도 화면이 쓰면 화면이
정본이다.

**`Card / Resume`(이어서 하기)은 2026-11-22에 옮겼다.** `1n-1`에 인스턴스가 없어
"규격을 읽을 자리가 없다"고 접어 두었는데, **라이브러리를 조회해 보니 게시돼
있었다**(`componentKey` 있음 · `updatedAt` 2026-10-15). **프레임 이름이 아니라
라이브러리를 봐야 했다** — 프레임이 `제안 · 미게시`여도 그 안의 심볼은 게시될 수 있다.

그동안 iOS 홈은 `openIntake`를 응답에서 읽기만 하고 **그리지 않았다.** Android는
`Card / Action` 바로 다음에 이 카드를 세운다(`HomeScreen.SheetTop`). **문답을 멈춘
사람이 홈에서 돌아갈 길이 없었던 것**이고, 기록 탭 목록까지 들어가야 보였다.

## 3. 대조하면서 발견한 것

마스터와 컴포넌트 설명이 어긋나면 **마스터를 따랐다.** 코드 주석에도 같은 내용을 적어
두었다.

**닫힌 것 스물넷.** 남은 넷(14 · 16 · 27 · 28)은 5장에 따로 적었다. 시안이 말하지 않는 자리라도
참조 구현이 규칙이나 낱말을 이미 정해 둔 것이 있고, 수치가 양쪽 같은 것도 있다. 그래서
디자인 트랙에 묻기 전에 Android를 먼저 본다.

**넷(1 · 4 · 6 · 8)은 두 플랫폼이 갈려 있던 자리이고 안드로이드에 맞췄다.** 마스터의
기하·스타일 정의와 컴포넌트 설명이 어긋나는 곳인데, 설명도 Figma가 적어 둔 값이고
Android가 그쪽을 따랐다. **두 플랫폼이 다르게 보이는 것이 둘 다 Figma 안에 있는 값을
고르는 것보다 나쁘다**고 보고 맞췄다. **iOS에서 더 고칠 자리는 남지 않았다.** 스물넷이 닫혔고, 남은 넷은 이쪽 코드가 아니라
다른 트랙의 일이다 — 아래 5장을 본다.

> 마스터와 설명이 어긋날 때의 기본은 여전히 **마스터**다(1장). 안드로이드가 설명 쪽을
> 이미 구현해 둔 자리에서만 그쪽으로 간다 — 그때는 고르는 문제가 아니라 두 플랫폼을
> 맞추는 문제다.

## 4. 가져오는 방법

1. Figma MCP로 세션을 연다(`create_session`, 파일 키 `OWKWtDt8lLQLmltq0ztT5O`).
2. `get_design_context`로 마스터 노드를 읽는다. **스크린샷을 함께 받아 눈으로 맞춘다.**
3. 반환된 React/Tailwind는 참고용 프로토타입이다. 토큰(`MMColor` · `MMFont` · `MMSpace` ·
   `MMRadius` · `MMElevation`)으로 바꿔 SwiftUI로 다시 쓴다. **원시 값을 박지 않는다.**
4. 색을 코드에서 읽을 수 없으면 **내보낸 SVG의 `stroke`/`fill`을 확인한다.** 짐작하지
   않는다 (Icon Button · Notice · Toggle · Date Cell을 이렇게 확정했다).
5. 아이콘·로고·일러스트는 `download_assets`로 **PDF**를 받아 에셋 카탈로그에 넣는다
   (벡터 보존). SwiftUI가 SVG를 읽지 못하고, **경로를 손으로 옮겨 그리지 않는다.**
6. `MMComponentGallery`에 한 줄 더하고 시뮬레이터에서 마스터와 나란히 본다.
7. `ComponentSpecTests`에 수치를 적는다.
8. 이 표에 노드 id와 함께 한 줄 더한다.

**Figma에 없거나 모호하면 멈추고 묻는다.** 비슷한 것으로 대신하거나 빈자리를 채우지
않는다. 마스터와 설명이 어긋나면 마스터를 따르고 3장에 적는다.

| -- | -- | -- |

### 글자를 키워 쓰면 보이는 것 둘 (2026-11-21)

**기본 글자 크기로만 보면 멀쩡하다.** 시뮬레이터를 `accessibility-extra-large`로
올리고 띄워서야 보였다(`xcrun simctl ui <udid> content_size accessibility-extra-large`).

먼저 확인한 것: **글자는 양쪽 다 커진다.** Android가 `sp`를 쓰고 iOS는 동적 타입을
따르므로 어긋남이 아니다. 어긋난 것은 **줄 수를 묶어 둔 자리**다.

| 자리 | 무엇이 어긋났나 | Android |
| -- | -- | -- |
| `1e-1` 브리핑 카드 제목 | `.lineLimit(1)`이라 **"복부 통…"으로 끊겼다.** 진료실에서 의사에게 보여 줄 카드의 제목이 사라진다 | `BriefCardBlock`에 `maxLines`가 없다 |
| `1j-3` 기록 상세 제목 | 같은 자리, 같은 까닭 | `RecordDetailScreen.Head`에 `maxLines`가 없다 |
| `1r-4` 고르는 칸 | 긴 병원 이름이 끊겼다 | `PickerField.PickerRow`가 `maxLines` 없이 `heightIn(min=)`으로 는다 |

셋 다 `.fixedSize(horizontal: false, vertical: true)`로 바꿨다. **기본 크기에서는 여전히
한 줄이라 시안과 같고**, 길어질 때만 줄이 는다. 배지가 첫 줄에 붙도록 `HStack`을
`.firstTextBaseline`으로 맞췄다.

`1r-4`의 칸은 테두리도 따라 늘려야 했다 — 줄 수만 풀면 둘째 줄이 56pt 상자 밖으로
샌다. `.frame(height:)`를 `.frame(minHeight:)`로 바꿨고, 이것이 Android의
`heightIn(min = controlLg)`와 같은 것이다. **기본 크기에서는 56으로 서서 시안과 같다**
— 띄워서 둘 다 확인했다.

**나머지 `.frame(height:)`는 그대로 둔다.** Android는 글자가 드는 칸마다
`heightIn(min=)`을 쓰고(`Button` · `Badge` · `Chip` · `SearchField` · `QuestionRow` ·
`SocialLoginButton`) iOS는 `.frame(height:)`라 못이 박혀 있지만, **컴포넌트 갤러리를
`accessibility-extra-large`로 띄워 보니 어느 것도 넘치지 않았다.** SwiftUI는 고정 높이에
글자를 가두지 않고, 이 토큰 높이들이 가장 큰 글자에도 넉넉했다. 보이지도 않는 차이를
열 군데 고치는 것은 범위 밖이다(CLAUDE.md 6장 3번). `Tab Bar`는 양쪽 다 고정이다.

**묶어 둔 나머지는 그대로 둔다.** `MMListRow`의 제목(한 줄 · 넘치면 줄임)과 요약은
마스터(`335:1114`)가 `whitespace-nowrap` · `text-ellipsis`로 그려 두었고 Android도
`maxLines = 1`이다(#294). 홈 카드 · 나브 바 · 배지 · 칩도 양쪽이 같다.

### 화면 프레임의 좌표를 직접 재 봤다 — `V2-00` (2026-11-21)

시안 대조는 지금까지 **눈으로** 했다(열여섯 장을 띄워 나란히 봤다). 마지막으로
**프레임의 좌표를 읽어 숫자로** 맞대 봤다. `get_metadata`가 자식마다 x · y · 폭 · 높이를
주므로, 쌓여서 나오는 값까지 검산할 수 있다.

`V2-00`(`3663:6862`, 360×812)으로 해 봤고 **열두 자리가 다 맞았다.**

| Figma | 뜻 | iOS |
| -- | -- | -- |
| Top Bar 56 · 거터 20 | | `MMSize.navBarHeight` · `MMSize.gutter` |
| Left Space 59 | 진행 표시를 **화면** 가운데에 묶는 자리 | `OnboardingMetrics.leftSpace` |
| Progress Wrap x=79 w=202 | 가운데 = 79+101 = **180** = 화면 가운데 | 59 + 건너뛰기 59를 빼면 202가 남아 같은 자리에 선다 |
| Onboarding Progress 62×24 | | 20 + 6×3 + 8×3 = 62 |
| Skip y=15 h=26 | `Body/L Strong` 26이 56 안에 가운데 | 같다 |
| Content y=56 · Copy y=72 | 위 여백 **72** | `topInset` |
| Title h=80 → Description y=104 | 사이 **24** | `spacing: s24` |
| Copy 끝 254 → Illustration y=278 | 사이 **24** | `spacing: s24` |
| Illustration 320×340 · 그림 326×326 at (-3, 7) | **제 크기 그대로 가운데** | 앞 절에서 고쳤다 |
| Footer y=720 h=92 · CTA y=12 h=56 | 위 **12** · 아래 **24** | `s12` · `s24` |

**쌓여서 나오는 값이 맞는지를 이 방법으로만 검산할 수 있다.** 예를 들어 "Left Space가
왜 59인가"는 좌표를 봐야 답이 나온다 — 건너뛰기 폭과 같게 둬야 진행 표시가 남은 폭이
아니라 **화면** 가운데에 선다. 그 59가 틀리면 눈으로는 "조금 치우쳤나" 정도로만 보인다.

**둘째 장 — `1r-1 · 캘린더 · 월`(`3663:15299`).** 여기도 다 맞았다.

| Figma | iOS |
| -- | -- |
| Content 위 **8** | `.padding(.top, s8)` |
| Month Head 320×48 · 버튼 48 · 제목 x=56 w=208 · 버튼 x=272 | `HStack(spacing: s8)` · `IconButton .l`(=48) · 제목 `maxWidth: .infinity` → 48+8+208+8+48 = 320 |

| FAB 48×48 · 오른쪽 **20** · 탭바 위 **20** | `gutter` · `tabBarHeight + 20` |
| **Calendar Grid 320×326** | 아래처럼 쌓여 정확히 326 |

그리드는 값이 하나도 적혀 있지 않고 **전부 쌓여서 나온다.** 좌표로 뜯어 보니 iOS와
한 칸씩 맞는다 — 위아래 12, 요일 줄 20(글 16 + 아래 4), 줄 간격 4, 주 5줄 × 46,
Week 6은 꺼짐, 범례 28(위 10 + 글 16 + 아래 2). **12 + 20 + 4 + (46×5 + 4×4) + 4 + 28

**셋째 장 — `1s-1 · 내 정보`(`3663:15766`).** 다 맞았다. Content 위 **8** · 구간 사이
**14**(아홉 자리가 전부 14다) · 아바타 **56**(마스터 기본 44보다 크다) · 아바타와 글

갈라 두었고, 시안의 `y=6` · `y=4`와 그대로 맞는다.

**넷째 장 — `1j-3 · 기록 상세`(`3663:15567`).** 다 맞았다. 점 **10** · 레일 **2**가
왼쪽 **4**(점 가운데) · 들여쓰기 **20** · 칸 사이 **16** · 키 폭 **52** · 머리 아래
**18** · 배지 좌우 8 · 위아래 3(= 24). **구분선이 눈에 띄는 자리였다** — 시안이 268이
아니라 **252**로 오른쪽만 16 비우는데, iOS도 `.padding(.trailing, s16)`이라 같다.

**다섯째 장 — `1n-1 · 홈`(`3663:7014`).** 다 맞았다. **시트가 배너를 28 덮는다**
(배너 400인데 시트가 y=372에서 시작한다) — iOS의 `HomeMetrics.overlap = MMRadius.xxl`

**여섯째 장 — `1e-1 · 브리핑 카드`(`3663:7335`).** 다 맞았다. Content 위 **12** ·

떨어진다) · 제목과 배지 사이 8 · 제목 줄과 환자 줄 사이 4 · 카드 바깥 구간 사이 **14** ·

준다**는 것을 `Badge`를 재다가 알았다. 좌표에서 역산하는 것과 달리 추측이 없다.

```
Card Pick(3663:14791)  →  px-[18px] py-[16px] gap-[10px]
  Checkbox(3663:14792) →  py-[14px] w-[24px]
```

**안쪽 여백은 16이 맞았다.** 18이 아니었다. 84가 나오는 까닭은 **체크박스가 제 줄
높이 52를 갖기 때문**이다 — 24 상자에 위아래 14다. 글 칸은 26 + 2 + 20 = 48뿐이라
줄 높이를 정하는 것은 체크박스 쪽이고, 16 + **52** + 16 = 84다.

`Checkbox` 마스터(`311:851`)의 설명이 같은 말을 한다 — **"박스 24 · 반경 8, 행 높이
52로 터치 하한을 넘습니다."** 처음부터 적혀 있던 값이다.

iOS의 `MMSelectBox`는 24 상자뿐이라 줄이 48로 서고 카드가 80이었다. 위아래 14를 줘
52로 세웠고 숫자로 묶었다(`ScheduleMetrics.cardPickHeight`). Android도 `CheckMark`가
24뿐이라 [#40](ANDROID-ISSUES.md)으로 올린다.

**배운 것** — 좌표에서 여백을 역산하면 "그 높이가 어디서 왔는지"를 틀리게 짚는다.
`84 − 48 = 36`을 보고 `18 + 18`이라고 읽었는데, 실제로는 여백이 아니라 **가운데 것이
자라 있었다.** 마스터의 여백이 궁금하면 `get_design_context`로 CSS를 읽는다.
같은 축을 `Badge`에도 써서 "폭 60"이 고정 폭이고 여백은 8이라는 것을 확인했다
(iOS · Android 둘 다 8이라 어긋남이 아니다).

### 좌표로 잰 것을 CSS로 되짚었다 — 넷, 다 맞았다 (2026-11-22)

`Card Pick`에서 좌표 역산이 틀렸던 터라, **좌표로 읽어 둔 여백을 `get_design_context`의
CSS로 되짚었다.** 같은 종류의 함정이 더 있는지 보려는 것이다. 특히 **작은 조작이 글
옆에 서는 컴포넌트**를 골랐다 — 거기서 자라는 것이 생긴다.

준 까닭이다.

**방법으로 적어 둔다** — 마스터의 여백이 궁금하면 좌표가 아니라 `get_design_context`의
CSS를 읽는다. 컴포넌트 설명도 같이 딸려 와서 "행 높이 52" 같은 말을 놓치지 않는다.

### 홈 배너가 이음매 없이 돌지 않았다 — Android `#322` (2026-11-22)

안드로이드 주석의 `#번호` 가운데 아직 안 본 것을 이어 훑다가 `#322`에서 걸렸다.
그쪽 `HomeBannerPager`는 **장 수를 10,000으로 잡고 가운데에서 시작한다.** 자리를
`% banners.size`로 접으면 마지막 장에서 0으로 돌아가는데, 그것은 "다음 장으로
넘어가는" 것이 아니라 **앞의 네 장을 거꾸로 되감는** 것이기 때문이다.

iOS가 `index = (index + 1) % pages.count`였다. 5장을 다 본 뒤 **되감겼다.**
같은 방법으로 고쳤다 — 자리는 늘 앞으로만 가고 그릴 때만 접는다. 값도 Android와
같은 10,000 · 가운데 시작이다.

함께: **장이 바뀔 때마다 처음부터 센다.** 전에는 4초를 제 박자로만 세서, 3.9초에
손으로 넘기면 0.1초 뒤에 또 넘어가 방금 넘긴 장을 보지 못했다. `task(id:)`의 키에
자리를 넣어 풀었다. Android도 `settledPage`가 바뀔 때마다 다시 센다.

**안 따라간 것이 하나 있고 까닭이 있다.** Android는 손이 닿아 있는 동안 기다린다 —
그쪽 페이저가 **닿는 순간 넘기던 동작을 취소**해서 배너가 아예 안 넘어갔기 때문이다
(그것이 `#322`의 본문이다). iOS는 자리를 바꾸는 것뿐이라 그럴 일이 없다. 그래도
맞춰 보려고 `DragGesture(minimumDistance: 0)`로 닿음을 받아 기다리게 했더니
**배너가 영영 멈췄다** — 페이저가 몸짓을 먹어 `onEnded`가 오지 않고 "닿아 있다"가
참으로 남았다. 걷어냈다. 세는 것을 자리마다 다시 시작하는 것으로 족하다.

**띄워서 확인했다** — 4.07초마다 꾸준히 넘어가고 5장을 지나 1장으로 멈춤 없이 돈다.
10,000칸을 미리 만들지도 않는다(메모리가 282 → 294MB에서 더 늘지 않았다).
`task(id:)`에 자리를 넣는 것이 세는 것을 끊지 않는지가 걱정이었는데, 로그로 자리가
5000 → 5005로 한 칸씩 가는 것을 봤다.

### 카드를 들고 일정 추가로 가지 않았다 — Android `#239` · `#245` (2026-11-22)

`#번호`를 이어 훑다가 또 하나 나왔다. **카드를 정해 놓고 일정 추가로 들어가는 길이
넷인데 셋이 카드를 흘리고 있었다.**

| 들어가는 길 | Android | iOS |
| -- | -- | -- |
| 카드만 있는 날 시트 "이 카드로 일정 만들기" | 그 카드를 들고 간다 | **흘렸다** |
| 홈 배너 1(`cardReady`) "진료 일정 잡기" | 들고 간다 | **흘렸다**(`{ _ in }`로 버렸다) |
| 브리핑 카드 "진료 일정 잡기" | 들고 간다 | **흘렸다** |
| 진료 후 기록의 재방문 확정 | 들고 간다 | 들고 갔다 |

**"이 카드로 일정 만들기"라고 적어 놓고 들어가서 다시 고르게 하면 두 번 고르는 꼴이다.**

**출처와 카드를 한 값으로 묶어 둔 것이 원인이었다.** iOS는 `followUpCardId` 하나로
"미리 고를 카드"와 "재방문인지"를 겸했다. 그래서 카드를 들려 보내면 **손으로 만든
일정까지 `visitFollowUp`으로 기록**된다 — 홈과 일자 화면이 그 값으로 "재진"을 적으므로
틀린 말이 남는다. Android는 `cardId`와 `followUp`을 **따로** 든다(`#239`는 미리 고르기,
`#245`는 출처다). 같게 갈라 두었다.

**함께 나온 것 — 홈 배너 3이 카드 번호로 `0`을 넘기고 있었다.** 들고 갈 카드가 없는
자리인데 `onScheduleCard(0)`이었다. 전에는 저장할 때만 끼워 넣어서 티가 안 났지만,
미리 고르게 바꾸면 **있지도 않은 0번 카드가 골라진 채로 저장된다.** `Int64?`로 바꿔
`nil`을 넘긴다.

**들고 온 카드는 체크된 채로 선다.** 전에는 저장할 때만 목록에 끼워 넣어서, 화면에는
안 골라진 것으로 보였다. Android의 `load()`도 받은 `cardId`를 고른 것에 더한다.

### 누른 일정이 열리지 않았다 — Android `#179` (2026-11-22)

**iOS는 일정 번호를 라우트에 들고 다니면서 한 번도 쓰지 않았다.**
`Route.calendarDay(date:appointmentId:)`가 있는데 받는 쪽이

두 자리가 어긋나 있었다.

1. **월 화면에서 누른 일정이 안 열린다.** 하루에 일정이 둘이면 누른 줄과 상관없이

2. **브리핑 카드의 "일정 보러가기"가 빈 화면으로 갔다.** 번호만 넘기고 날짜 자리에

   `HomeRepository.date(from: "")`로 날짜를 못 만들어 `if let`이 떨어지고 **아무것도
   그리지 않는다.** 누르면 흰 화면이다. `BriefCardAppointment`가 `date`를 이미 들고
   있어서 함께 넘기면 되는 자리였다.

이 길은 **일정이 있는 카드에서만** 선다. 화면을 띄워 눌러 보는 대조에서 1e-1을
볼 때마다 일정 없는 카드였던 모양이다 — 열한 상태를 다 봤다고 적어 두었는데도
남아 있었다.

`pick(_:id:)`로 갈라 두고 숫자로 묶었다 — 누른 것 · 그 날에 없는 번호(지운 일정으로
돌아오는 경우) · 번호 없음 · 일정 없음 넷이다.

없으며, 시간 시트는 휠이 284로 선다. **"못 본다"가 아니라 "길을 안 찾았다"였다.**

### 같은 카드로 다시 잡은 일정이 "초진"으로 떴다 — Android `#272` (2026-11-22)

`#245`로 출처와 카드를 가른 뒤, 그 줄의 다음 문장이 `#272`였다.

**재진인지는 `followUp` 하나로 갈리지 않는다.** Android는
`followUp || cards.any { it.picked && it.visited }`다 — **이미 진료를 마친 카드를
골랐으면** 그것도 재진이다. 뒤의 것이 없으면 같은 카드로 다시 잡은 일정이 일자
화면과 홈에서 **"초진"**으로 뜨는데, 기록 상세(`1j-3`)는 같은 진료를 **재방문**으로
적는다 — **한 진료가 두 화면에서 다르게 불린다.**

iOS는 `isFollowUp`만 봤다. `CardListItem.Kind.card(id:visited:)`가 이미 `visited`를
들고 있어서 값은 다 있었다. 같은 규칙으로 바꾸고 숫자로 묶었다(고른 마친 카드 ·
고르지 않은 것 · 아직 안 간 카드 · 카드가 아닌 줄).

**함께 본 것들** — `#304`(화면이 가려지면 받아쓰기를 멈춘다)는 iOS도 `onDisappear`에서
`dictation.stop()`이라 같다. `1e-1-X` 내보내기 시트(`3663:7479`)도 14 · 4 · 16 · 8 ·
8 · 8로 시안 그대로였다. **시트가 다 어긋났던 것이 아니라 `1r-4`의 둘만 그랬다.**

### 카드 배지가 다녀온 뒤에도 "진료 전"으로 남을 수 있었다 — `Backend#101` (2026-11-22)

Android가 **"진료를 마쳤는지는 상세 응답에 없어 목록에서 본다"**고 적어 두고, 카드
상세를 읽을 때 목록을 함께 불러 `visited`를 채운다.

빼고 보내면 `1e-1`의 배지가 다녀온 뒤에도 영영 "진료 전"**이다. `nil`이 `false`로
접히는 자리라 화면에는 아무 표시도 나지 않는다.

값이 **비어 올 때만** 목록을 본다. 서버가 채워 주면 호출이 한 번도 더 나가지 않고,
빼고 보내면 Android와 같아진다. 고친 카드는 새 id를 받아서 옛 id로는 목록에 없을 수
있고 그때는 "진료 전"으로 남는다 — Android도 같다.

**이 축에서 함께 확인하고 넘어간 것들** — `#219`(한 번 연 카드는 다시 읽지 않는다,

배지가 빠지지 않는다. 시안의 그 인스턴스가 꺼 둔 것이다.

세우면 42종이 한 화면에 선다. 로그인도 서버도 필요 없다. 스크롤로 끝까지 훑었고
**어느 칸에서도 어긋난 것이 보이지 않았다.** 화면도 같은 방법으로 묶어 `TabView`에
얹으면 옆으로 넘기며 본다 — 스플래시 · 로그인 · 온보딩 · `1b-4` · `1c-5`가 한 빌드에
다 선다.

**이 축은 아무것도 못 찾았고, 그럴 만하다.** 색은 팔레트 43값을 기계로 맞댔고
(2026-11-21), 크기는 마스터 42종을 다 쟀다. 그림이 걸러 낼 것이 남아 있지 않다.
**숫자로 먼저 맞춘 뒤의 그림 대조는 확인이지 수색이 아니다** — 반대 차례였으면
"비슷해 보인다"로 넘어갔을 자리가 여럿이었다.

### 다 만들어 둔 화면에 길이 없었다 — 병원 찾기 (2026-11-22)

가짜 서버로 화면을 눌러 보다가, 브리핑 카드의 **"변경"이 자리표시자로 갔다** —
`hospitalPick / 아직 그리지 않았다`. 그런데 **`HospitalPickView`는 진작 서 있다.**
`1m-B`는 "화면" 표에도 들어 있고, 증상 정리 흐름과 진료 후 흐름 **안에서는** 잘 뜬다.

`MainTabView.visitDestination`의 `switch`에 `.hospitalPick` 갈래가 없어서
`default`의 자리표시자로 떨어지고 있었다. **길만 없었다.**

고치면서 `Route.hospitalPick`이 **카드 번호를 들고 가게** 했다. 고른 병원을 그 카드에
적고 돌아와야 "변경"이 뜻을 갖는다(`CardRepository.update(cardId:clinic:)`가 이미
있었다). 건너뛰면 그대로 돌아온다 — 화면이 "아직 정하지 않았다면 건너뛰어도 돼요"라고
적어 둔 그대로다.

**이 자리는 어느 축으로도 안 잡혔다.** 좌표·마스터·토큰·문구·`#번호`는 **그려진 것**을
보고, 테스트는 **모델**을 본다. 자리표시자는 그릴 것이 없어 좌표가 없고, 라우트에
갈래가 빠진 것은 컴파일도 통과한다(`default`가 받는다). **눌러 보는 것 말고는
걸릴 그물이 없었다.**

**그래서 나머지 라우트도 기계로 훑었다.** `Route`의 스물한 갈래를 `destination`의
`switch`들과 맞대어 보니 받지 않는 것이 여섯이다 — `intakeDone` · `onboardingIntro` ·
`profileSetup` · `profileComplete` · `visitNote` · `visitRecord`. **다만 그 여섯은
아무도 밀지 않는다**(`Route.swift` 밖에서 쓰이지 않는다). 흐름 안에서 그려지는
화면들이라 라우트가 필요 없는데 enum에만 남아 있는 것이다. 지금 깨지는 자리는 아니라
그대로 두되, **라우트가 있다고 길이 있는 것은 아니라는 것**을 여기 적어 둔다.

**길을 이어 놓고 나서 하나가 드러났다** — 메이트의 "진료 후 기록"이 `hospitalPick`을
가리키고 있었다. 그 라우트가 자리표시자였을 때는 티가 안 났는데, 이어 놓고 보니
**병원을 고른 뒤 아무 일도 없는 막다른 길**이었다. 진료 후 기록 흐름(`VisitFlowView`)은
카드가 있어야 열리는데 메이트는 어느 카드인지 모른다. Android도 이 명령에서는
`openTabRoot(tab)`으로 뿌리만 열고 화면에 넘긴다. iOS에는 그 넘김이 없어 **홈**으로
보낸다 — 거기 배너 1이 실제 카드를 들고 "진료 후 기록하기"를 띄운다.
**고치면서 새로 만든 흠이라 같은 커밋에서 닫는다.**

### 문답 줄의 배지를 진행도로 짐작하고 있었다 (2026-11-22)

못 본 화면을 보려고 홈 픽스처에 **이어서 할 문답**을 넣었다. `1j-4`에 줄이 섰는데
배지가 **"임시 저장"**이다. 픽스처는 `questions_confirmed: false`였다.

`BriefCardListModel`이 서버 값을 안 보고 **진행도로 짐작하고 있었다.**

```swift
questionsConfirmed: open.step >= open.total,   // ← 3/3이면 확정으로 쳤다
```

**3/3은 AI 문답이 끝난 것이지 확정한 것이 아니다.** 질문 고르기 화면까지 가서
"다음"을 안 누르고 나간 사람도 3/3이다. 그 사람의 줄이 "임시 저장"으로 떠서,
**카드를 만들 준비가 끝난 것처럼 보인다.**

`HomeDTO`가 바로 이 함정을 적어 두고 있었다 — *"**서버의 `ended`로 가르지 않는다** —
그것은 AI 채팅이 끝난 순간이라 질문 고르기 도중에 나간 문답도 참이다."* `ended` 대신
진행도를 쓴 것뿐 같은 실수다. **경고를 적어 두고 그 옆에서 같은 짓을 했다.**

서버의 `questions_confirmed`가 `HomeOpenIntake`에 실리지 않아 목록이 지어낼 수밖에
없었다. 그 값을 끝까지 들고 가게 하고 숫자로 묶었다(확정 전 3/3 · 확정 · 진행 중).
화면에서 "임시 저장" → **"작성 중"**으로 바뀌는 것을 확인했다.

### 같은 방법으로 `1p-T`를 열었더니 둘이 더 나왔다 (2026-11-22)

`#186`이 "변이 프레임을 안 열어 본 탓"이었으니, **다른 `-T` · `-A` 변이도 열었다.**

**배운 것** — 문구 대조는 **문장 목록**이 아니라 **자리마다** 해야 한다. 같은 말이
다른 화면에 쓰이면 목록 대조는 통과한다.

### `1e-1`·`1j-3`·`1m`의 변이를 다 열었다 — 하나 나왔다 (2026-11-22)

변이 프레임 축의 마지막이다. 여섯 장을 열었다 — `1m`(진료 후 병원 찾기 `3663:14329`) ·
`1j-3-X`(카드 펼침 `3663:15624`) · `1e-1-E`(`3663:7529`) · `-E2`(`3663:7569`) ·
`-A`(`3663:7609`) · `-A2`(`3663:7649`).

**하나가 나왔다 — 값을 다 지운 줄.** `-E2`의 둘째 줄(`3663:7584`)이

> 비어 있음 — 카드에 표시되지 않아요

를 세우고 그 줄의 ×를 감춘다(`3663:7586`). **두 기기가 다 빠뜨렸다.** Android의

없애는 것은 다른 일"이라고 못박아 두었고 iOS도 같아서 **줄은 남는데**, 남은 줄이 빈

**이어서 `1e-1`의 열한 상태를 다 열었다**(일정 없음 `3663:7335` · 일정 보기 `7393` ·

읽기 셋의 하단 버튼 모양(Primary · Outline · Tonal)과 글, 툴팁 두 줄, 삭제 확인의 두
문장, 일정 시트의 14 · 4 · 20 · 8이 다 맞았다. 머리 배지가 모든 상태에서 "작성중"인 것은
**3장 15번에서 이미 닫은 자리**다 — 마스터의 기본값이고, 카드는 만들 때부터 확정이라
상세에 설 수 없다.

**내보내기 시트(`1e-1-X`)에서 셋이 나왔다.**

1. **「이름·나이 가리기」가 꺼진 채로 열렸다.** 시안의 토글이 켜져 있고 Android도
   `maskPatient = true`에 "처음에는 가린다 — 카드를 남에게 보이는 자리라 덜 내보내는
   쪽이 기본"이라고 적어 두었다. iOS만 `false`여서, **모르고 내보내면 이름과 나이가
   그대로 나갔다.**
2. **가리기가 화면의 카드까지 바꿨다.** `patientLine`이 토글만 보고 있어서, 켜 둔 채
   시트를 닫으면 **내 화면의 내 이름이 가려진 채 남았다.** 토글은 내보낼 이미지를 정하는
   값이다. Android는 `capturingMasked`를 찍는 동안만 켠다. iOS도 `isCapturing`과 함께
   보게 했다.
3. **미리보기가 토글을 따라가지 않았다.** `MMExportPreview`가 마스터의 예시 글을 그대로
   들고 있어서 **토글이 무엇을 바꾸는지 보이는 곳이 하나도 없었다** — 1번과 2번이 겹쳐
   눈에 안 띈 까닭이기도 하다. Android처럼 그 카드의 제목과 환자 줄을 넣는다. 안쪽
   막대는 글이 아니라 모양이라 마스터 그대로 둔다.

셋 다 Android가 맞았다. **"켜져 있는 그림"을 상태 하나로 넘기지 않는다** — 시트의
토글은 단면이 곧 기본값이다.

**마지막으로 남은 변이 넷도 열었다** — `1j-3-R`(재방문 누적 `3663:15690`) ·
`1q-1-E`(진료 후 기록 편집 `3663:14477`) · `1j-4-D2`(목록 여럿 고르기 `3663:7145`) ·
`1j-4-DC`(여럿 삭제 확인 `3663:7156`). **넷 다 맞았다.**

- `1j-3-R`: 배지가 `진료 2회`, 둘째 줄이 `병원 · 09.12 초진 · 09.26 재방문`(오래된 차례),
  칸은 최신이 위다. 가장 최근 기록의 재방문이 `증상 재발 시에만`이라 **예정 칸이 서지
  않는 것**까지 iOS의 `pendingStep`과 같다.
- `1q-1-E`: 편집 중에 머리의 아이콘 버튼과 AI 설명 줄이 빠지고 **진료 메모는 남는다.**
  상단 오른쪽이 `취소`, 아래가 `진료 후 기록 삭제`다. 재방문 줄의 강조도 편집 중에는
  빠지는데 `MMKVEditRow`가 강조를 받지 않아 그대로다.
- `1j-4-D2`: 머리의 오른쪽이 달마다 **그 달에서 고른 수**(`1장 선택됨`)이고 아래 버튼은
  **전체 수**(`2장 삭제`)다. 고른 줄은 테두리가 서고, 편집 중에는 셋째 줄과 chevron이
  빠진다.
- `1j-4-DC`: `브리핑 카드 2장을 삭제할까요?` · `연결된 진료 기록은 남고 선택한 카드는
  사라져요.` 오른쪽 버튼이 그림에서도 `취소`로 남아 있는데 `Dialog` 마스터의 기본값이다
  — 머리 배지의 "작성중"과 같은 종류다(3장 15번).

`1r-4-C` · `1r-4-S` · `1b-3-T` · `1n-1-4`·`-5` · 메이트 세 상태는 앞선 작업에서 이미
열어 두었다. **이로써 와이어프레임의 변이 프레임을 다 열었다.**

**배운 것**: 변이 축에서만 나온 어긋남이 이제 셋이다(`#186` · `1p-T`의 글과 마이크 ·
이것). 기본 프레임은 아무리 재도 **상태가 바뀌어야 비로소 그려지는 것**을 보여 주지
않는다. 기본 프레임의 좌표를 다 쟀다는 것은 변이를 쟀다는 뜻이 아니다.

### 문구를 **자리마다** 다시 맞댔다 — 둘 (2026-11-22)

`1p-T`에서 배운 것이 "문구 대조는 문장 목록이 아니라 자리마다 해야 한다"였는데, 그
축을 기계로 돌린 적이 없었다. Android `strings.xml` 815건을 두 방향으로 돌렸다.

1. **자리가 다른 것**: 값이 iOS에 있기는 한데 그 키가 속한 도메인 밖에만 있는 것.
   38건이 걸렸고 **36은 제자리였다** — 공용 컴포넌트(`MMEmptyState`의 "다시 시도",
   `MMSeveritySlider`의 다섯 단계, `MMChatComposer`)에 있는 것들이다. 나머지 둘도
   들여다보니 맞았다(`1q-1` 툴팁은 `\n`이 있어 걸린 것이고, 카카오 버튼은 디자인
   시스템 자리다).
2. **iOS에 아예 없는 것**: 59건. 대부분은 이미 아는 것이다 — 호출어·온디바이스 LLM
   (1차 제외) · Share Extension(M4) · 이미 올린 어긋남(#28 · #30 · #31 · #33 · #34 ·
   #35) · iOS가 일부러 다르게 푼 것(`login_restore_failed`는 iOS가 복구 때 서버를
   부르지 않아 실패할 자리가 없다).

**여기서 둘이 나왔다.**

**하나 — 탈퇴가 거절돼도 아무 말이 없었다.** `MainTabView`가
`_ = await app.session.withdraw()`로 결과를 버리고 있어서, 서버가 거절하면 창만 닫히고
화면은 그대로다. **되돌릴 수 없는 동작인데 됐는지 안 됐는지를 알 수 없다.** Android의
`account_withdraw_failed`가 "탈퇴하지 못했어요. 계정은 그대로 있어요"라고 적는다.
`onWithdraw`가 결과를 돌려주게 하고 `MyProfileView`의 오류 자리에 세웠다.

**둘 — 시간 미정으로 저장한 일정의 시각을 채울 길이 없었다**(Android `#230`).
일정 추가는 시각 없이도 저장되는데(`canSave`는 날짜만 본다), 저장하고 나면 그 값을
넣을 자리가 앱 어디에도 없었다. 알림도 그만큼 거칠게 선다 — 시각이 있으면 24시간 전,
없으면 전날 오후 7시다. Android는 **시각이 없는 일정만** 눌러서 `1r-4`를 `PATCH`로
열어 푼다("시간 미정으로 저장하고 나면 그 값을 채울 자리가 어디에도 없었다").

iOS도 같게 했다 — 라우트에 `appointmentId`를 더하고, 일자 화면의 일정 카드가
**시각이 비었을 때만** 눌리며, `ScheduleAddModel`이 그 날 목록에서 일정을 찾아 값을
채우고 저장이 `PATCH`로 나간다. 서버에 일정 하나를 id로 읽는 경로가 없어 그 날의
목록에서 찾는 것도 Android와 같다. 출처(`origin`)는 보내지 않는다 — 이미 저장된
일정이 어디서 왔는지는 고친다고 바뀌지 않는다.

**가짜 서버로 눌러서 확인했다.** 시각이 `null`인 일정을 내주고 캘린더 → 22일 → 일정
카드를 눌렀더니 병원·날짜·카드가 채워진 채 열렸고, 10:30을 고르고 저장하니
`PATCH /api/me/appointments/1 {"scheduled_time":"10:30", …}`이 찍혔다. **새로 만들지
않았다** — 그러면 같은 일정이 둘이 된다.

**배운 것**: `#번호` 대조를 "끝까지 훑었다"고 적었는데 `#230`이 걸리지 않았다. 그때
번호를 **Android 코드 주석에서만** 긁었고, 이 건은 Android의 `CLAUDE.md` 산문에만
있었다. 번호는 코드 주석과 문서 양쪽에서 긁어야 한다.

### `#번호`를 **문서 산문에서도** 긁었다 — 열일곱 더 (2026-11-22)

`#230`을 놓친 까닭이 "번호를 Android 코드 주석에서만 긁었다"였으니, 같은 그물을 문서
쪽에도 쳤다. Android의 `*.md`에서 긁은 번호와 코드 주석에서 긁은 번호를 맞대니
**문서에만 있는 것이 열일곱**이었다(#139 · #153 · #159 · #163 · #165 · #167 · #171 ·
#172 · #194 · #208 · #213 · #214 · #217 · #221 · #222 · #237 · #242).

**열여섯은 이미 같거나 이쪽 일이 아니었다** — 타임라인 세 단계(#171 · #221)와 `List Row`
제목 `Heading/S`(#237) · `Empty State`의 채움 없는 행동(#217) · 온보딩 건너뛰기(#213)는
이미 그대로였고, 화면 전환(#214)은 Android가 `navigation-compose`의 기본값을 고치려고
들인 품이라 iOS에는 옮길 것이 없다(0장 — 수단은 iOS 것으로 다시 쓴다). 나머지는 백엔드
계약이거나 Android가 걷어낸 화면(#159 · #165 · #194)이다.

**하나가 나왔다 — 저장 조건(`#312`, 문서에서 `#172` 옆에 있다).**
Android는 `canSave = hospital != null && date != null && !cardMissing`인데 iOS는
`on != nil` 하나였다. **병원 없이도 저장됐다.** 그러면 일자 화면의 일정 제목이
**빈 줄로 선다** — 제목을 병원 · 진료과 · 목적으로 짓기 때문이다. 시안도 저장하기를
병원이 차는 순간 켠다(`1r-4`는 꺼져 있고 `1r-4-B`는 병원만 차고 켜져 있다). 병원과
날짜를 함께 보게 고쳤다.

**카드까지 요구할지는 열어 둔다**(3장 43번). Android는 새 일정에 가져갈 카드를 하나
이상 요구하는데 그쪽 문서가 **사용자 결정**이라고 적어 두었고, 이 저장소에는 "카드 없이
'다음 주 치과'만 적을 수 있어야 한다"가 적혀 있다. 근거가 양쪽 다 사람의 판단이라
기계로 고를 자리가 아니다.

겸해서 **고치러 연 일정에서는 예약 문자 안내를 감췄다** — 이미 저장된 일정을 문자로
채울 일이 없다(Android의 `showShareHint`도 같다).

**병원을 필수로 만들고 나서 하나가 더 드러났다 — 카드의 병원을 안 쓰고 있었다.**
Android는 `load()`에서 `picks.pickedClinic()`으로, 카드를 고르는 순간에는
`hospital = hospital ?: clinic`으로 **빈 병원 칸을 고른 카드의 병원으로 채운다**(`1r-4-B`).
iOS는 둘 다 없어서, 카드를 정해 놓고 들어오는 네 길(카드만 있는 날 시트 · 홈 배너 ·
브리핑 카드 · 재방문 확정)이 **이미 아는 병원을 다시 찾게** 만들었다. 병원이 선택일
때는 티가 안 났는데 필수로 바꾸니 **한 걸음이 두 걸음이 된다.**

`CardListItem`에 `clinic`을 들려 보내 채운다. **메타 줄에서 되읽지 않는다** — 거기에는
`"병원 미정"`이 섞여 있어서 그 말이 병원 이름으로 저장된다. **이미 적힌 병원은 덮지
않고**, 카드를 푸는 것으로 지우지도 않는다(사람이 고쳐 둔 값을 되돌리게 된다).

**규칙 하나를 바꾸면 그 규칙에 기대어 숨어 있던 것이 드러난다** — 이번 것은 "병원이
선택이라 안 채워도 그만"이던 자리였다.

**병원 고르기가 정말 서는지 확인하다가 둘이 더 나왔다.** 병원을 필수로 만들었으니 그
화면에서 병원을 고르는 길이 막혀 있으면 저장 자체가 불가능해진다. 길은 서 있었는데,
**하단 버튼이 "브리핑 카드 만들기"라고 적고 있었다.** 누르면 카드가 생기는 것처럼
읽히는데 실제로는 칸만 채우고 돌아온다.

Android는 목적이 **셋**이고(`AFTER_VISIT` · `BEFORE_VISIT` · `SCHEDULE`) `forExistingCard`를
따로 든다. 규칙은 **"브리핑 카드 만들기"는 정말 카드를 만드는 길에서만**이다(`#229`) —
그 외에는 전부 "완료"다. 문구(제목 · 안내)는 `AFTER_VISIT`만 다르고 나머지 둘은 같다.

iOS는 목적이 둘뿐이라 **두 자리가 틀려 있었다** — 일정 추가의 병원 칸과, **브리핑
카드의 "변경"**이다. 뒤의 것은 오늘 라우트를 이어 놓으면서 닿게 된 자리라, 길을 열자
그 끝의 글이 틀린 것이 같이 드러났다. `.schedule`을 더하고 `forExistingCard`를 받게
했다.

**길을 이어 놓으면 그 끝에 있던 것도 처음으로 읽힌다** — 자리표시자였을 때는 아무도
그 버튼의 글을 보지 않았다.

### 반대 방향으로도 훑었다 — 지어낸 글은 없다 (2026-11-22)

지금까지 문구 대조는 **Android → iOS** 한 방향이었다. 반대로 **iOS에만 있는 글**을
뽑으면 §1 3번이 금한 "지어낸 문구"가 걸린다. 주석을 뺀 Swift 글자 상수에서 Android
`strings.xml`에 없는 것 **179개**가 나왔다.

**화면에 서는 글은 전부 근거가 있었다.** 179의 내역은 — 보간이 섞인 줄(`\(count)장을
삭제할까요?`처럼 Android에서는 `%1$d`라 글자만으로는 안 걸린다) · `#Preview`와
`MMComponentGallery`의 예시 글 · 메이트 명령의 정규식 · Android에 같은 자리가 없는
오류 글(화면마다 "…하지 못했어요") · iOS만 쓰는 말(`MMElevation`의 주석 상수)이다.

확인한 것 셋 — `1r-2`의 삭제 확인 본문은 Android와 같고(마침표만 이쪽에 있는데 `1e-1-DC`
등 다른 시안 본문이 다 마침표를 찍는다), 일자 화면의 다녀온 카드 메타("브리핑 카드 ·
진료실에서 보여줌")는 `1r-2-A2`에서 온 것이며, `1m-12`의 안내는 **두 줄 다** 시안과
같다("9월 12일 일정에 등록해둔 병원이에요. / 다른 곳에서 진료받았다면 바꿀 수 있어요.").
제목의 띄어쓰기까지 같다 — 시안이 여기서만 **"진료 받은"**으로 띄우고 `1m`에서는
"진료받은"으로 붙이는데, iOS가 자리마다 그대로 따르고 있었다.

**고친 것은 하나뿐이고 화면 밖이다** — `MMSettingRow`의 `#Preview` 샘플이
`"확정 시 24시간 전"`으로 띄워 적고 있었다. 화면(`MyProfileModel`)과 Android는
`"확정시"`다. 미리보기 샘플은 다음 사람이 복사해 가는 자리라 맞췄다.

**이 축은 "없는 것"이 아니라 "지어낸 것"을 찾는다** — 두 방향이 잡는 것이 다르다.

### 오늘 고친 것을 눌러서 확인했다 — 내 고침의 흠 하나 (2026-11-22)

가짜 서버를 다시 세우고 오늘 고친 것들을 하나씩 눌러 봤다.

**내보내기 셋이 다 맞았다.** 시트를 열면 「이름·나이 가리기」가 **켜진 채**로 서고,
미리보기는 그 카드의 제목과 **가린** 환자 줄을 보이며, 시트 뒤의 카드는 **가려지지
않은** 줄 그대로다. 가린 줄은 `김OO · 여 · 2026.09.04 작성`으로 Android와 글자까지
같다 — 나이는 "OO세"로 바꾸지 않고 **뺀다**(마스터의 샘플만 "OO세"다. Android가
"숫자를 바꿔 적으면 틀린 정보가 찍힌다"고 적어 두었다).

**편집 모드도 맞았다** — 내보내기 아이콘 · AI 설명 줄 · 알러지 경고가 다 빠지고 테두리가
서며, 고치면 상단이 `취소`에서 `확인`으로 바뀐다.

**그런데 내가 오늘 넣은 빈 줄 안내가 한 줄로 잘려 있었다.** `"비어 있음 — 카드에
표시되지 않…"`. `overlay`로 얹었더니 **한 줄짜리 `TextField`의 높이에 갇힌** 것이다.
시안의 그 줄은 80으로 **두 줄**이다. 안내를 `ZStack`의 **아래에 깔아** 줄 높이를 잡게
하고(빈 `TextField`는 캐럿 말고 그릴 것이 없어 그대로 비쳐 보인다) 다시 띄워 두 줄로
서는 것을 확인했다.

**이번 것은 "안 보이던 자리"가 아니라 "내가 오늘 만든 자리"였다** — 고친 것을 눌러
보지 않았으면 잘린 글이 그대로 나갔다. 단위 테스트는 글자만 보니 잡지 못한다.

**일정 추가의 세 가지도 눌러서 확인했다.** 빈 화면에서 저장하기가 **꺼져 있고**(병원이
비어서), 카드를 고르는 순간 병원 칸이 **`서울OO병원`으로 채워지며** 저장하기가 켜지고,
그와 동시에 **예약 문자 안내가 사라진다**. 마지막 것은 시안 그대로다 — `1r-4`(병원
미등록)에만 있고 병원이 찬 `1r-4-B`에는 없다. 셋이 한 번의 탭으로 같이 움직이는 것을
보고서야 "규칙 하나가 세 자리를 건드린다"가 눈에 들어온다.

### 컴포넌트 목록을 라이브러리로 다시 셌다 — 하나가 빠져 있었다 (2026-11-22)

"안 옮긴 것"은 **2026-11-20 Figma 기준으로 확정**해 둔 목록이다. 그 뒤로 게시된 것이
있으면 막아 둔 것이 풀리므로 다시 셌다. `search_design_system`으로 라이브러리를
조회했다.

- **`Toast`는 없다.** `Notice`와 `Dialog`의 설명이 "Toast와 구분됩니다"라고 말할 뿐
  마스터가 없다. 내보내기 저장 알림([#10](https://github.com/Medical-Mate/IOS/issues/10))은
  그대로 막혀 있다 — iOS가 안 그리는 것이 맞다.
- **`Body Map`도 없다.** 인체도([#1](https://github.com/Medical-Mate/IOS/issues/1))도 그대로다.
- **`Card / Resume`은 게시돼 있었다.** `componentKey`가 있고 `updatedAt`이 2026-10-15다.

마지막 것이 빠진 자리였다. 2장 2절에 "미게시"라고 적어 둔 근거가 **프레임 이름**
(`홈 · 신규 컴포넌트 (제안 · 미게시)`)이었는데, 프레임 이름과 심볼의 게시 상태는
다른 값이다. 같은 프레임의 `Link / On Image` · `Card / Action` · `Card / Schedule`
셋은 화면이 쓰고 있어서 옮겼고, 넷째만 "화면이 안 쓰니 규격을 읽을 자리가 없다"로
남았다 — **라이브러리를 한 번도 안 봤다.**

그동안 **iOS 홈은 `openIntake`를 읽기만 하고 그리지 않았다.** 서버가 "멈춘 문답이
있다"고 알려 주는데 화면에 아무것도 서지 않아서, 문답을 멈춘 사람이 **홈에서 돌아갈
길이 없었다**(기록 탭 목록까지 들어가야 보인다). Android는 `Card / Action` 바로
다음에 이 카드를 세운다. 마스터대로 `MMCardResume`을 만들고 홈 시트의 같은 자리에
세웠다. 아랫줄은 Android `home_resume_step`과 같은 `두통 · 1단계까지 했어요`다.

**배운 것**: "미게시"라고 적을 때는 **무엇을 보고 그렇게 적었는지**를 함께 적어야
한다. 프레임 이름을 보고 적은 것과 라이브러리를 보고 적은 것은 다르고, 뒤에 그
기록을 읽는 사람(나 자신이었다)은 구별하지 못한다.

### 막아 둔 기록을 증거와 맞대어 봤다 — 넷은 유효, 하나는 틀렸다 (2026-11-22)

`Card / Resume`이 "프레임 이름만 보고 미게시로 적은" 자리였으니, **같은 종류의 기록을
전부 다시 봤다.** "없다 · 못 받았다 · 막혀 있다"고 적어 둔 것들이다.

| 기록 | 다시 본 방법 | 결과 |
| -- | -- | -- |
| `Toast` 마스터가 없다([#10](https://github.com/Medical-Mate/IOS/issues/10)) | 라이브러리 조회 | **유효.** `Notice`·`Dialog` 설명이 "Toast와 구분됩니다"라고 말할 뿐 마스터가 없다 |
| 인체도 컴포넌트가 없다([#1](https://github.com/Medical-Mate/IOS/issues/1)) | 라이브러리 조회(`Body Map`) | **유효.** 0건 |
| 네이버·Apple·Google 로고를 못 받았다([#7](https://github.com/Medical-Mate/IOS/issues/7)) | **Android 저장소의 `res/`를 뒤졌다** | **유효.** 그쪽에도 없다. 배너 사진은 거기서 찾았지만 이것들은 양쪽 다 없다 |
| 앱 아이콘이 비어 있다([#8](https://github.com/Medical-Mate/IOS/issues/8)) | 라이브러리 조회 + Android `mipmap/` | **유효.** Android는 Android Studio 템플릿 그대로다(`ic_launcher_background`/`_foreground`). Figma에는 **앱 아이콘 프레임이 없고** `Logo Symbol`의 `Gradient` 변이 설명이 "앱 아이콘·스플래시"라고 적을 뿐이다. 그 심볼은 이미 받아 뒀다(`logo-symbol-gradient`). **배경과 여백을 얹으면 내가 디자인하는 것이라** 1장 4번대로 멈춘다 |
| `Card / Resume`이 미게시다 | 라이브러리 조회 | **틀렸다.** 게시돼 있었다 — 위 절 참조 |

**다섯 중 하나가 틀렸다.** 틀린 하나는 유일하게 **라이브러리가 아니라 프레임 이름을
근거로 적은 것**이었다. 나머지 넷은 근거가 라이브러리이거나 다른 저장소의 파일이라
다시 봐도 같았다.

**겸해서 셈이 낡았는지도 봤다.** 아이콘은 두 저장소의 이름을 직접 맞댔고 **47 대 47,
이름까지 같다**(iOS의 `icon-` 접두사와 Android의 `ic_` 접두사만 다르다. Android 쪽
`drawable/`에는 로고 6 · 런처 2 · 카카오 1이 섞여 있어 그것을 뺀 수다).

그리고 라이브러리 조회가 돌려준 **`updatedAt`이 모두 `2026-10-15`다.** 게시된
라이브러리가 그 뒤로 바뀌지 않았다는 뜻이고, 그래서 **셈이 낡아서 틀릴 일은 없었다** —
`Card / Resume`도 "새로 게시된 것"이 아니라 **처음부터 게시돼 있던 것을 잘못 읽은
것**이다. 목록을 다시 세는 것보다 **근거를 다시 보는 것**이 맞는 대응이었다.

### 새로 세운 카드를 띄웠더니 진행도가 틀려 있었다 — Android `#176` (2026-11-22)

`Card / Resume`을 만들고 **또 눈으로 안 봤다.** 지난번에 그래서 잘린 글이 나왔으니
띄웠고, 이번에도 하나 나왔다. 다만 이번 것은 내가 만든 자리가 아니라 **원래 있던
자리**였다.

카드가 `3/3`으로 섰다. 픽스처의 `progress_current`·`progress_total`이 3·3이라
맞아 보였는데, Android가 그 값을 **쓰지 않는다**고 적어 두었다(`#176`):

> `progressCurrent` / `progressTotal`은 문답 **왕복**을 센 것이고 상한이 **20**이다.
> 그대로 찍으면 "20단계 중 0단계까지 답했어요"가 되는데 환자가 보는 증상 정리는
> 세 단계다.

iOS는 두 자리에서 그대로 찍고 있었다 — 새 `Card / Resume`과 **원래 있던 기록 목록의
줄 메타**(`오늘 · N단계 중 M단계`)다. 뒤의 것은 오늘 전부터 있던 버그이고, 픽스처가
늘 3·3이라 한 번도 드러나지 않았다.

규칙은 Android와 같다 — 세션은 부위·강도를 고른 뒤에 생기므로 **늘 3단계에 있고**,
질문 고르기에서 "다음"을 눌렀으면 셋을 다 마친 것이다. `IntakeProgress`로 뽑아
두 자리가 같이 쓴다. 다시 띄우니 `2/3`이고 링도 2/3만 찬다.

**픽스처가 "맞아 보이는 값"이면 축이 안 돈다** — 3·3은 서버가 줄 수 있는 값 중
**유일하게 틀린 규칙과 맞는 값**이었다.

### 토큰 설명을 끝까지 읽었다 — 날것의 팔레트 둘 (2026-11-21)

`fg/muted`의 설명("글자에 쓰지 않습니다")에서 어긋남이 나왔던 것을 떠올려, **남은

### 컴포넌트 숫자 상수를 기계로 맞대어 봤다 (2026-11-21)

앞서 **바탕값**(팔레트 43 · 간격·크기·반경 26 · 타이포 15 · 아이콘 47)은 맞대어 봤지만,

`Tooltip Bubble`이었다.**

### 내보내기를 만들었다 (2026-11-21)

아래 두 단추를 실제로 잇는 동안 **같은 격리 함정을 한 번 더 밟았다.** 받아쓰기의
`authorize()`를 고친 직후에 쓴 코드인데, `PHPhotoLibrary.performChanges`의 블록도
사진 라이브러리의 제 큐에서 돌아가서 `@MainActor`에 묶인 채로 두면 똑같이 앱이
죽었다. **이 함정은 "콜백을 받는 자리"마다 있다** — `nonisolated`로 풀었다.

옮긴 규칙과 바꾼 수단:

| Android | iOS |
| -- | -- |
| 스크롤 **안쪽**을 통째로 찍는다. 바깥에 두면 화면에 보이는 높이만 찍힌다 | 같은 `column`을 화면과 내보내기가 함께 쓴다. 시트가 "카드 전체가 긴 이미지 한 장"이라고 적어 둔 그대로다 — 카드만 찍으면 알러지 경고와 묻고 싶은 것이 빠진다 |
| 찍는 동안 내보내기 단추를 감춘다 | `isCapturing`으로 같게. 찍은 그림에 단추가 없는 것을 확인했다 |
| PNG로 넣는다 | PNG로 넣는다. `creationRequestForAsset(from:)`은 JPEG으로 굳히므로 PNG를 파일로 써서 넣는다 — 글자가 빽빽한 카드라 획 둘레가 번지면 안 된다 |
| `Pictures/진료메이트` 앨범 | **앨범을 만들지 않는다.** 앨범을 찾으려면 사진첩 읽기 권한이 필요한데, 카드에 복용약 · 기저질환 · 알러지가 들어 있어 넣기만 하는 권한(`addOnly`)으로 두는 것이 낫다고 봤다. 규칙은 가져오고 수단은 iOS 것으로 다시 쓴 자리다(CLAUDE.md 0장) |
| `브리핑카드_yyyyMMdd_HHmmss.png` | 같다. 테스트가 못박는다 |
| 공유는 앱 캐시를 거쳐 받는 앱에만 | `UIActivityViewController`에 이미지를 바로 넘긴다 |

**띄워서 넷을 다 확인했다** — 저장(사진에 1080×2464 PNG가 들어갔다) · 공유 시트 ·
가리기(나이가 빠진 `김OO · 여 · 2026.09.04 작성`) · 단추가 빠진 그림.

**남은 것 하나는 여전히 막혀 있다.** 저장 결과를 알리는 글을 Android는 Toast로
띄우는데 그 마스터가 Figma의 `Archive`에 있다. 지금은 **못 넣었을 때만** 시트 안에
한 줄로 적고, 넣은 때에는 사진 앱이 알리므로 적지 않는다.

**공유 시트의 미리보기 자리가 비어 있다.** 앱 아이콘이 아직 비어 있어서다
([#8](https://github.com/Medical-Mate/IOS/issues/8)) — 내보내기 쪽 문제가 아니다.

### 눌러도 아무 일이 없는 단추 (2026-11-21)

받아쓰기에서 "눌러 봐야 나온다"는 것을 배우고 **제품 화면의 단추를 전부 세어 봤다.**
스물둘 가운데 **둘이 시트만 닫고 아무 일도 하지 않는다** — `1e-1-X` 내보내기 시트의

**나머지 스무 개는 다 이어져 있다.** 갤러리와 `#Preview`의 빈 `action: {}`은 미리보기라
세지 않았다.

### 받아쓰기를 눌러 보고 나온 것 (2026-11-21)

안드로이드 `#304`("화면이 가려졌다 — 다음 화면으로 갔거나 **앱이 뒤로 갔다**. 듣던
것을 멈춘다")를 따라가다 받아쓰기를 처음으로 **실제로 눌러 봤다.** 세 가지가 나왔다.

| 자리 | 무엇이 | 확인 |
| -- | -- | -- |
| **허락을 처음 내줄 때 앱이 죽었다** | `SFSpeechRecognizer.requestAuthorization`은 답을 아무 스레드에서나 돌려주는데 `authorize()`가 `@MainActor`에 묶여 있어, 그 콜백이 메인이 아닌 곳에서 continuation을 깨우자 **Swift 6의 격리 검사가 그 자리에서 앱을 죽였다**(`_swift_task_checkIsolatedSwift` → `dispatch_assert_queue_fail`). **허락을 내주고 마이크를 처음 누른 사람에게만** 일어나 화면을 아무리 띄워도 보이지 않았다 | **고쳤고 확인했다.** `nonisolated`로 바꾸니 권한 창 둘을 지나 멀쩡히 선다 |
| 앱이 뒤로 가도 마이크가 열려 있었다 | `onDisappear`는 화면을 나가는 것만 잡는다. 앱이 뒤로 가는 것은 잡지 못해 다른 앱에 가 있는 동안 계속 듣는다. 안드로이드는 `onScreenHidden()`으로 막아 두었다 | `willResignActive`를 `DictationController` 자신이 듣게 했다 — 화면마다 잊지 않으려면 마이크를 쥔 쪽이 들어야 한다. **코드로만 확인했다**(시뮬레이터에는 마이크가 없어 듣는 상태를 유지할 수 없다) |
| 들어오는 소리가 없으면 CoreAudio가 앱을 죽인다 | 입력 형식이 0채널 · 0Hz로 오는데 그대로 탭을 걸면 `AURemoteIO::Initialize()`가 `abort()`한다. **던지는 오류가 아니라 잡을 수도 없다.** 다른 앱이 마이크를 쥐고 있을 때도 같은 길이다 | 탭을 걸기 전에 형식을 보고 "마이크를 열지 못했어요"로 받친다. **막는 쪽이 맞다고 보고 넣었지만 시뮬레이터에서 이 길을 다시 태우지는 못했다** |

**이 셋은 시안 대조로도, 규칙 대조로도 안 나온다.** 기능을 실제로 눌러야 나온다.

### 키보드가 올라올 때 (2026-11-21)

**Android가 네 자리에 못을 박아 두었는데 iOS는 셋을 비워 두고 있었다.** 안드로이드는
`adjustResize` + `WindowInsets.ime` + `bringIntoView`로 풀었고, iOS는 `ScrollViewReader`가
같은 자리를 맡는다. 시뮬레이터에서 실제로 키보드를 올려 보고서야 보였다.

| 자리 | Android가 못박은 것 | iOS |
| -- | -- | -- |
| `1p` 진료 후 메모 | **칸의 아랫변을 늘 보이게 한다**(#183). 적을수록 칸이 아래로 자라는데 키보드가 올라오면 방금 친 글자와 세는 칸이 그 뒤로 들어간다. **칸 자체가 아니라 바로 아래 줄을 부른다** — 칸이 화면보다 길어지면 윗변에 맞춰져 커서가 도로 가린다 | 아무것도 하지 않아 **칸을 누르는 순간 아랫변과 `0 / 300`이 저장 버튼 뒤로 들어갔다.** 같은 방법으로 풀었다 |
| `1r-4` 할 일 추가 | 줄이 **늘어난 때만** 따라가고 지우거나 처음 불러온 때에는 움직이지 않는다. 키보드가 멎기를 120ms 기다렸다 옮긴다 | 따라가지 않았다. `.onChange(of:)`에 같은 규칙을 넣었다 |
| `1r-4` 새 할 일 줄 | **뜨자마자 커서를 가져간다**(`UnderlinedField`). 더하기를 누른 뒤 빈 줄을 한 번 더 눌러야 적는 것은 "추가"를 두 번 누르게 하는 것이다 | 커서를 주지 않아 한 번 더 눌러야 했다. `@FocusState`로 줬다 |
| `1c-2` 증상 문답 | 끝으로 보내는 값이 여덟이다 — 그중 **질문 줄 수**와 **직접 적기 시작**이 있다(#310) | 셋만 보고 있었다(말 수 · 답하는 중 · 끝남). **문답이 끝난 뒤 서는 추천 질문이 늘거나 빈 칸이 열리면 키보드 뒤에 남았다.** 둘을 더했다 |

`1r-2` 일자 상세는 양쪽 다 할 일을 더하거나 고치지 않아(시안의 어느 상태에도 추가가
없다) 손댈 자리가 없다.

**마이크 단추가 세는 칸을 덮는 것은 두 기기가 같다** — 그래서 한쪽만 고치지 않았다.
키보드가 올라오면 떠 있는 마이크가 본문 영역의 아래 끝으로 내려오는데 그 자리가 마침
칸의 아랫변이다. Android도 `BottomEnd` + gutter라 똑같이 겹친다. **시안에는 키보드가
올라온 상태가 없어** 무엇이 맞는지 고를 근거가 없다(1장 4번).

**기록으로만 두지 않고 결정 대기로 올렸다**
([#11](https://github.com/Medical-Mate/IOS/issues/11)). 두 기기가 같다는 것은 "맞다"가
아니라 "같이 틀렸을 수도 있다"는 뜻이고, 정해지면 **두 저장소에 같이** 반영해야 한다.

### `fg/muted`는 글자에 쓰지 않는다 (2026-11-21)

토큰 자체의 설명이 못박는다:

> **3.78:1 — 글자에 쓰지 않습니다. 비활성 아이콘·장식 획 전용. 플레이스홀더와 캡션은
> fg/subtle을 씁니다**(이 앱에서는 그것들이 유일한 안내라 장식이 아닙니다)

**시안 쪽이 그 말을 어기고 있던 자리가 둘이었다.** `1r-4`의 고르는 칸 안내 문구
(`3663:14777`)와 로그인 고지가 `fg/muted`로 그려져 있다. Android는 둘 다 `fg/subtle`로
구현해 두었고(`PickerField.kt` · `LoginScreen.kt`) 그쪽에 맞췄다 — 3장 1 · 4 · 6 · 8번과
같은 판단이다(**설명도 Figma가 적어 둔 값이고, 두 플랫폼이 갈리는 쪽이 더 나쁘다**).
2장이 이미 "로그인 화면의 다른 안내는 반드시 기준을 넘는 색으로 둔다"고 적어 둔
